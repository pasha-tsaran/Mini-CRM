# Telegram: настройка и локальная проверка

Интеграция использует официальный [Telegram Bot API](https://core.telegram.org/bots/api)
и [deep linking](https://core.telegram.org/bots/features#deep-linking).
Клиент сам начинает личный чат. Поиск пользователя по телефону не выполняется:
номер — контактные данные; получатель определяется по `user_id` и `chat_id`.
Username клиента не требуется. Неофициальные API и пользовательские аккаунты не используются.

## Создание бота и секреты

1. В официальном Telegram откройте **@BotFather**, выполните `/newbot`, задайте
   имя и username бота. Сохраните выданный токен локально в менеджере секретов.
2. Создайте отдельный случайный секрет CRM длиной не менее 32 символов в менеджере
   паролей. Это **другой секрет**, не токен Telegram. CRM и бот должны получить
   одинаковое значение `CRM_BOT_API_TOKEN`.
3. Скопируйте `.env.example` в `.env` и заполните настройки либо задайте
   переменные окружения перед запуском. Не присылайте токены в чат,
   не вставляйте в исходники, README, команды с открытым текстом или скриншоты.
   `.env` исключён из Git и автоматически читается всеми тремя компонентами
   из корня проекта. Окружение процесса имеет приоритет. `.env.example`
   содержит только имена и безопасные значения по умолчанию.

| Настройка | Где нужна | Значение |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | Бот, обработчик | Токен от BotFather |
| `TELEGRAM_BOT_USERNAME` | CRM, бот | Username без `@` |
| `CRM_BOT_API_TOKEN` | CRM, бот | Общий секрет интеграции |
| `CRM_BASE_URL` | Бот | `http://127.0.0.1:5000` |
| `DATABASE_PATH` | CRM, обработчик | Один и тот же файл, по умолчанию `instance/crm.sqlite3` |
| `BOT_STATE_PATH` | Бот | Отдельный файл, по умолчанию `instance/bot-state.sqlite3` |
| `UI_TIMEZONE` | CRM, обработчик | Одинаковый пояс, по умолчанию `Europe/Moscow` |

Если заполнен `.env`, ручной ввод ниже не нужен: переходите к запуску компонентов.
После изменения настроек перезапустите все три компонента.

Альтернатива через PowerShell, из корня проекта, в каждом из трёх терминалов (значения секретов
вводятся скрыто; для удобства можно задать все переменные во всех терминалах):

```powershell
$env:TELEGRAM_BOT_USERNAME = Read-Host 'Username бота без @'
$env:CRM_BASE_URL = 'http://127.0.0.1:5000'
$env:DATABASE_PATH = 'instance/crm.sqlite3'
$env:BOT_STATE_PATH = 'instance/bot-state.sqlite3'
$env:UI_TIMEZONE = 'Europe/Moscow'
$telegramSecret = Read-Host 'Токен BotFather' -AsSecureString
$env:TELEGRAM_BOT_TOKEN = [System.Net.NetworkCredential]::new('', $telegramSecret).Password
$crmSecret = Read-Host 'Общий секрет CRM из менеджера паролей' -AsSecureString
$env:CRM_BOT_API_TOKEN = [System.Net.NetworkCredential]::new('', $crmSecret).Password
Remove-Variable telegramSecret, crmSecret
```

Linux/macOS, Bash, в каждом терминале:

```bash
read -r -p 'Username бота без @: ' TELEGRAM_BOT_USERNAME
read -r -s -p 'Токен BotFather: ' TELEGRAM_BOT_TOKEN; printf '\n'
read -r -s -p 'Общий секрет CRM: ' CRM_BOT_API_TOKEN; printf '\n'
export TELEGRAM_BOT_USERNAME TELEGRAM_BOT_TOKEN CRM_BOT_API_TOKEN
export CRM_BASE_URL='http://127.0.0.1:5000'
export DATABASE_PATH='instance/crm.sqlite3'
export BOT_STATE_PATH='instance/bot-state.sqlite3'
export UI_TIMEZONE='Europe/Moscow'
```

Не выводите окружение целиком для диагностики. HTTP-клиент не журналирует URL
Bot API, заголовки и ответы; ошибки содержат только безопасный числовой код.
Перенаправления HTTP запрещены, чтобы не передать авторизацию другому адресу.

## Три компонента

После установки по [README](../README.md) запустите по одной команде в каждом
из трёх подготовленных терминалов:

```powershell
# Терминал 1: CRM
.\.venv\Scripts\python.exe -m flask --app app.main:create_app run --host 127.0.0.1 --port 5000
```

```powershell
# Терминал 2: long polling
.\.venv\Scripts\python.exe -m bot.main
```

```powershell
# Терминал 3: очередь уведомлений
.\.venv\Scripts\python.exe -m workers.notifications
```

Для Linux/macOS замените `.\.venv\Scripts\python.exe` на `.venv/bin/python`.
Остановка каждого процесса — Ctrl+C. Используйте **один процесс CRM, один
polling-бот и один обработчик очереди**, без Flask reloader. Импорт Flask не
запускает фоновые процессы. Public domain и webhook не нужны. Для ранее
использовавшего webhook бота его нужно отключить средствами официального API
перед polling; приложение не меняет настройки Telegram автоматически.

CRM принимает только локальные подключения. Бот дополнительно проверяет,
что `CRM_BASE_URL` указывает на loopback. Компьютеру нужен исходящий HTTPS-доступ
к `api.telegram.org`. Российское расположение сервера само по себе доступность
не гарантирует. При отсутствии секретов CRM работает без интеграции, а команды
бота/обработчика завершаются с русским списком недостающих настроек.

## Создание заявки и подписка

В личном чате: `/start` → «Оставить заявку» → имя → собственный контакт кнопкой
«Поделиться номером» или ручной ввод → описание → проверка данных → «Отправить».
Доступны «Изменить», «Отменить» и `/cancel`. Контакт с чужим или отсутствующим
`user_id` не принимается; ручной ввод проверяет формат, а не владельца номера.
В группе бот предлагает личный чат и не сохраняет текст/контакт пользователя.

Успех показывается только после commit CRM. Получатель фиксируется из личного
чата, где оформлена заявка. Разные заявки с одинаковым телефоном разрешены.
После сбоя с неизвестным результатом черновик нельзя менять или отменять до
повторной отправки: так сохраняется один идентификатор и исключается дубль.
Если до отправки выбран пункт «Изменить», поля вводятся заново.

При создании через сайт появляется ссылка **«Получать уведомления в Telegram»**,
если в CRM заданы username бота и секрет интеграции. Ссылка содержит случайный
43-символьный код на 30 минут. Открыв бота, клиент подтверждает подключение.
До подтверждения бот не раскрывает номер или содержание заявки. После привязки
приходит текущий статус; старая история автоматически не рассылается.

Код хранится в CRM как SHA-256; бот тоже сохраняет только хеш входного кода.
Ссылка выдаётся лишь в ответе создания (`Cache-Control: no-store`) и текущем
уведомлении формы. Она отсутствует в общем списке и после обновления страницы;
повторная выдача ссылки не реализована. Не пересылайте ссылку: обладатель кода
может подключить заявку до первого использования. Истёкший, неизвестный или уже
использованный другим запросом код отклоняется. Точный повтор подтверждения
после потери ответа безопасно возвращает прежнюю привязку.

В таблице менеджера видны источник «Сайт»/«Telegram», подключение уведомлений и
состояние последней доставки: «ожидает», «отправлено», «ошибка» (при временном
сбое — «ошибка, повтор ожидает»). Состояние обновляется при открытии/обновлении
страницы. Токены и Telegram ID не выводятся в таблице.

## Защищённый HTTP API

Оба маршрута требуют `Authorization: Bearer <CRM_BOT_API_TOKEN>`. Авторизация
проверяется до чтения JSON. Без секрета — `401 unauthorized`, неверные поля —
`422 validation_error`, несовместимый повтор/неверный код — `409 integration_conflict`.
Формат остальных ошибок совпадает с основным API.

`POST /integrations/telegram/leads`:

```json
{"submission_id":"draft-1234567890123456","name":"Иван","phone":"+79991234567","message":"Хочу консультацию","telegram_user_id":123,"telegram_chat_id":123}
```

Ответ `201` содержит обычную заявку (`id`, `name`, `phone`, `message`, `status`,
`created_at`). Сочетание постоянного `submission_id` и нормализованных данных
возвращает прежнюю заявку; другое содержание или получатель даёт конфликт.
ID отправки — строка 16–64 символа из букв, цифр, `_`, `-`. Пример бота использует UUID.
Telegram ID — положительные целые; user_id и chat_id должны совпадать для личного чата.

`POST /integrations/telegram/bind`:

```json
{"code":"<код из ответа создания>","request_id":"binding-1234567890123456","telegram_user_id":123,"telegram_chat_id":123}
```

Ответ `200`: `{"id":42,"subscribed":true}`. Вместо исходного кода бот передаёт
его SHA-256; хеш тоже является секретом подтверждения до использования.
Подключение с чужим телефоном или произвольным id не предусмотрено. Открытый
`POST /lead` отвергает Telegram ID и источник как неизвестные поля. Открытый
локальный `GET /leads` остаётся API менеджера: это **не система авторизации
клиентов**, и публиковать его в интернете нельзя.

## Сохранение и восстановление

- При обновлении старой базы перед добавлением таблиц SQLite backup API создаёт
  согласованную копию в `instance/backups/` (или `backups/` рядом с выбранной БД).
  `leads` не перестраивается, строки не удаляются. Повторный запуск безопасен.
  Универсальный механизм миграций будущих изменений колонок не реализован.
- История реальных переходов, статус и `notification_outbox` фиксируются одной
  транзакцией. Тот же статус не создаёт событие; повторное открытие и новый переход
  создают новое. У старых заявок история остаётся пустой до первого изменения.
- Время события хранится в UTC; сообщение использует его, а не время отправки.
  Для Москвы подпись «МСК», для других поясов — имя IANA и фактическое смещение UTC.
  Если историческое время не известно, сообщение прямо говорит об этом.
- Обработчик фиксирует попытку и аренду задачи на 60 секунд, закрывает транзакцию,
  затем обращается к Telegram. После падения просроченная аренда подхватывается
  автоматически. Сеть не блокирует транзакцию менеджера.
- Таймауты: CRM 10 секунд, отправка Telegram 15, long polling 25 с сетевым
  таймаутом 35 секунд. Сетевые ошибки/5xx повторяются с задержками 10, 20, 40…
  секунд, максимум час; `retry_after` Telegram может увеличить задержку.
  Пока старое событие ожидает повтора, более новое по той же заявке не отправляется.
- Успех хранит `message_id` и время подтверждения. 403 прекращает повторы для
  этого чата и отмечает подписки заблокированными; 400/401/404 дают конечную ошибку.
  Автоматического восстановления заблокированной подписки и панели повторного
  запуска конечных ошибок нет. Исправление токена не переотправляет такие задачи.
- Бот сначала сохраняет всю пачку входящих событий и offset одной транзакцией
  в `bot-state.sqlite3`, затем подтверждает её следующим getUpdates. Там же
  сохраняются черновики и очередь ответов. Повторный update_id игнорируется.
  После commit CRM и потери ответа повтор с тем же ID не создаёт новую заявку.
  Черновики с неопределённым исходом сохранены; клиенту предлагается повторить.
- После успешного ответа бота персональный текст обработанного события и
  доставленного ответа удаляется из записей. Незавершённые черновики остаются
  в базе; автоматическая очистка старых записей/истории не предусмотрена.

Сохраняйте обе SQLite-БД и защищайте их правами файловой системы: они содержат
персональные данные. Для ручного резервирования остановите три процесса и
скопируйте файлы; для восстановления используйте согласованную копию и те же пути.
Не удаляйте БД состояния для «перезапуска»: потеряются черновики и дедупликация.

Гарантия одной заявки обеспечивается уникальным идентификатором в CRM.
**Абсолютная однократная доставка сообщений не гарантируется:** если Telegram
принял сообщение, но ответ потерялся до фиксации успеха, повтор может отправить
его ещё раз. Уникальный event_key предотвращает дубли задач, но не этот сетевой случай.

## Проверки и реальная доставка

Автоматические тесты используют временные SQLite и подменённый Telegram API,
не выполняют запросов в Telegram и не требуют токенов:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pytest -q --cov=app --cov=api --cov=database --cov=models --cov=bot --cov=integrations --cov=workers --cov-report=term-missing
```

Итог текущих проверок находится в [отчёте](telegram-verification.md).
**Реальная доставка не проверена: секреты не настроены.** После локальной настройки:

1. Запустите три компонента. В личном чате оформите вымышленную заявку и убедитесь,
   что бот сообщил её номер, а CRM показывает источник Telegram.
2. Повторите «Отправить»: второй заявки быть не должно. Измените статус на
   «В работе» и сверьте номер, статус и время сообщения; повтор того же статуса
   не должен отправлять новое сообщение.
3. Создайте заявку на сайте, откройте ссылку, подтвердите привязку и проверьте
   сообщение текущего статуса. Попытайтесь использовать ссылку из другого чата:
   она должна быть отклонена.
4. Остановите обработчик, измените статус, запустите обработчик: ожидающее
   уведомление должно отправиться. Перезапустите бота посреди черновика и продолжите.

Промышленной авторизации менеджеров, публичного развёртывания, VK-бота и внешней
проверки телефонов нет. Перед любым сетевым доступом нужна защита **всего** API
и доступа менеджеров; секрет интеграции защищает только два новых маршрута.
